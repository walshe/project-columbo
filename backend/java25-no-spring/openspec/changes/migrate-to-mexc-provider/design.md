## Context

`CandleIngestionService` routes each active asset to a `MarketDataProvider` via `Map<AssetVenue, MarketDataProvider> providersByVenue`, keyed purely by `asset.venue()` — a mechanism already proven twice (Binance SPOT/FUTURES, then Tiingo EXCHANGE) to accept a new provider with zero changes to scheduling, locking, or orchestration. Adding MEXC follows the identical shape: one new `AssetVenue` value, one new `MarketDataProvider` implementation, one new map entry.

Live verification against MEXC's real API (2026-08-26) confirmed:
- `GET /api/v3/klines?symbol=BTCUSDT&interval=1d&limit=3` and the same call against a tokenized-stock symbol (`AAPLONUSDT`) both return an array of 8-field rows — `[openTime, open, high, low, close, volume, closeTime, quoteVolume]` — byte-identical in shape to `BinanceMarketDataProvider.toCandle`'s existing parsing. No new parsing logic is needed beyond copying that method.
- `/api/v3/klines` costs weight 1, IP-limited at 500/10s; `/api/v3/exchangeInfo` costs weight 10, same window. At the asset counts this system runs (dozens, not thousands), this is not a meaningfully constraining limit — no throttle needed, unlike Tiingo's 50/hour.
- No API key is required for either endpoint — both are public market data, unauthenticated.
- `/api/v3/exchangeInfo` returned 2123 symbols total. Every symbol includes `fullName` (human name) and `conceptPlates` (array of tag strings). Tokenized real-equity pairs carry `"mc-trade-zone-xStocks"` in `conceptPlates` — confirmed present on `SBETONUSDT` ("SharpLink Gaming"), `TSLAONUSDT` ("Tesla (Ondo)"), `TLTONUSDT` ("iShares 20 Year ETF"), etc.
- The `baseAsset`-suffix heuristic (ends with `ON`) the user's own research proposed as a fallback signal produces a real false positive against live data: `BOSONUSDT` is a genuine crypto token (Boson Protocol) whose base asset happens to end in "ON", and it is **not** tagged `xStocks`. This rules out the suffix check as anything but a weak secondary hint — `conceptPlates` is the only signal used in this design.
- `rateLimits` in the `exchangeInfo` response body is an empty array on MEXC (unlike Binance, which populates it) — the weight/window figures above come from MEXC's own API docs, not introspectable from the response itself.

## Goals / Non-Goals

**Goals:**
- MEXC becomes the sole active market-data provider across all three briefed asset classes (CRYPTO, STOCK, ETF), reachable through the existing `providersByVenue` routing with no orchestration changes.
- Binance and Tiingo are fully dormant (zero active assets, app startable without `TIINGO_API_KEY`) but not deleted — reversible by reactivating rows and restoring the required-env check, no redeploy needed for the rollback path.
- Total active asset count stays bounded (no repeat of the `fix-pipeline-connection-pool-exhaustion` incident), even though a single provider now covers every asset class.

**Non-Goals:**
- No attempt to onboard MEXC's full 2123-symbol universe — "for everything" is read as "every *asset class* this system tracks", not "every symbol MEXC lists."
- No general multi-provider abstraction beyond what already exists (`MarketDataProvider` interface, `providersByVenue` map) — same philosophy as the Tiingo change.
- No deletion of `BinanceMarketDataProvider`/`TiingoMarketDataProvider` code, tests, or migrations — "for now" means data-level, not code-level.
- No change to how `TradingViewUrl` builds chart links beyond what its existing generic branch already does.
- No W1 handling changes — MEXC's klines are daily-bar EOD-equivalent same as Binance's, W1 continues to be derived by the existing D1 rollup path.

## Decisions

**1. New `AssetVenue.MEXC` (not reuse of `SPOT`).**
Unlike Tiingo's `EXCHANGE` (deliberately generic, "a real exchange, e.g. Tiingo", in case a second real-exchange provider is ever added), `AssetVenue.MEXC` is named after the provider directly: MEXC covers CRYPTO *and* tokenized STOCK/ETF through the exact same single client and endpoint, so there's no shared abstraction boundary left to generalize over the way EXCHANGE generalizes "a real securities exchange." Reusing `SPOT` was rejected for the same reason it was rejected for Tiingo: `BinanceMarketDataProvider.defaultBaseUrlFor`/`klinesPathFor` switch on `SPOT` specifically meaning *Binance* spot, and overloading it risks a future refactor accidentally routing a MEXC asset into the Binance client.
- *Alternative considered:* reuse `AssetVenue.EXCHANGE` since it's already "not Binance-spot-or-futures." Rejected — `EXCHANGE` already has a settled meaning (real securities exchange via Tiingo, paired with a verified `tradingview_ref`) and MEXC assets don't use `tradingview_ref` at all (see Decision 4); conflating the two would make `EXCHANGE`'s semantics ambiguous for no benefit.

**2. `MexcMarketDataProvider` copies `BinanceMarketDataProvider`'s structure almost verbatim.**
Same constructor pattern (`(httpClient)` / `(httpClient, baseUrl)` for testability), same `/api/v3/klines?symbol=&interval=1d&startTime=&endTime=` query shape, same 8-field row parsing (open time, O/H/L/C, volume at index 5, close time, quote volume at index 7 — confirmed identical field order live). The only real differences from Binance: no venue-based path/host switch (MEXC has one product, one base URL, one path), and no API key.
- *Alternative considered:* a shared abstract base class for the two nearly-identical providers. Rejected as premature — matches this codebase's stated philosophy of not building shared abstractions until a third near-duplicate actually shows up; two structurally-similar-but-independent classes is an acceptable amount of duplication for now.

**3. Asset classification (CRYPTO vs STOCK vs ETF) happens once, at onboarding time, not per-ingestion-run.**
A one-off classification pass over `/api/v3/exchangeInfo` (via a script or a throwaway `main`, not a class that ships in the running service) determines each onboarded symbol's `asset_class` before it's written into a seed migration. `CandleIngestionService` never needs to call `exchangeInfo` or re-classify anything at ingestion time — `asset_class` is a stored column, same as every other provider's assets today.
- Classification rule, in order: `conceptPlates` contains `"mc-trade-zone-xStocks"` and `fullName` (case-insensitive) contains `"etf"` → `ETF`; `conceptPlates` contains `"mc-trade-zone-xStocks"` alone → `STOCK`; otherwise → `CRYPTO`. The `baseAsset`-suffix heuristic is **not** used (see Context — proven unreliable against live data).

**4. MEXC assets do not populate `tradingview_ref`; `TradingViewUrl` needs no code change.**
`TradingViewUrl.generateUrl`'s non-`EXCHANGE` branch already does `provider.name() + ":" + fullSymbol` (e.g. `"MEXC:AAPLONUSDT"`) for any venue other than `EXCHANGE`/`FUTURES`-suffix cases. This is untested against TradingView's actual symbol resolution for MEXC's tokenized-stock tickers specifically — flagged as a task requiring a live spot-check (open one or two generated URLs) before calling this change done, same verification discipline as the original Tiingo `tradingview_ref` seeding.

**5. New asset universe: user-curated top-100-by-market-cap lists (crypto/stock/ETF), live-matched against MEXC, then capped at 50/50 for crypto/stock (mirroring `V22`'s per-class cap) with ETF kept uncapped since it never approaches 50.**
Rather than remapping today's active Binance/Tiingo symbols, the user supplied three top-100-by-market-cap lists (crypto, stock, ETF) to serve as the new universe's source ranking. Each was live-matched against MEXC's `exchangeInfo` (2026-08-26):
- **Crypto**: 93/100 have a direct `<TICKER>USDT` pair on MEXC. The 7 without one are dropped outright, not substituted — 5 are stablecoins/gold-pegged tokens (`DAI`, `GHO`, `EURC`, `XAUT`, `PAXG`, which also have no meaningful "trend" for SuperTrend regardless of tradeability) and 2 are rival exchanges' own tokens not listed on MEXC (`LEO`, `GT`).
- **Stock**: 64/100 have a MEXC tokenized (`xStocks`/Ondo) wrapper. The 36 without one are dropped, not substituted — 30 are non-US primary listings (Ondo's wrapper set is overwhelmingly US-listed; this covers Saudi Aramco, Samsung, 8 Chinese A-shares, Tencent, and most large European/UK/Japanese/Canadian names) plus 4 surprising US misses with no wrapper at all (`BRK.A`, `MS`, `HD`, `PM`). One approximation: MEXC only wraps Alphabet's Class A (`GOOGL`), so `GOOGLONUSDT` substitutes for the user's `GOOG` (Class C) — a different share class, not an exact match, but tracks near-identically. 7 tickers have *two* MEXC wrappers (an `-ON` "Ondo" and a separate `-X` "xStock"/Backed-issued one, e.g. `NVDAONUSDT`/`NVDAXUSDT`) — `-ON` is chosen by default for consistency across the list.
- **ETF**: only 18/100 have a MEXC wrapper — Ondo/xStocks' ETF coverage is far narrower than its stock coverage (broad-market/factor/commodity/leveraged names like `SPY`, `QQQ`, `IWM`, `GLD`, `TQQQ`, `SOXX`; none of the Vanguard/Schwab lineup, sector SPDRs beyond none, bond funds beyond `AGG`/`SGOV`, or the Japan/Taiwan-listed and Ireland-domiciled-UCITS entries in the user's list).
- **Cap decision**: 93+64+18 = 175 tradeable assets before capping — within range of the 247-asset count that caused the `fix-pipeline-connection-pool-exhaustion` incident (unbounded one-virtual-thread-per-asset fan-out against a 10-connection pool). Bounding ingestion concurrency directly (a small fix in `CandleIngestionService`) was offered as an alternative to preserve the full curated list, but the user chose to keep `CandleIngestionService` untouched and instead trim crypto and stock to the top 50 *tradeable* names by market-cap rank each (walking down past untradeable ranks to backfill, not just truncating at rank 50) — exactly mirroring `V22`'s existing 50-per-provider-class cap pattern. ETF's 18 matches stay uncapped, nowhere near 50.
- The full resulting 118-asset list (50 CRYPTO + 50 STOCK + 18 ETF), including which specific tickers were dropped and the rank-51+ reserves for crypto/stock, is recorded in [asset-list.md](asset-list.md) rather than duplicated here.
- *Alternative considered:* bound ingestion concurrency instead of trimming (see above) — offered to the user as the recommended option since it preserves the full curated 175-asset list without reducing coverage, but the user explicitly chose the trim-to-cap path to avoid touching `CandleIngestionService` at all.

**6. No rate limiter needed in `MexcMarketDataProvider`.**
500 req/10s (weight 1 for klines) against ~90 assets, even fetched back-to-back with zero delay, finishes in under 2 seconds of budget — nowhere close to the limit even accounting for the existing per-asset `POLITE_DELAY_MS` pacing `CandleIngestionService` already applies uniformly. No throttle, no retry-budget math required (contrast Decision 4 in the Tiingo design, which was necessary specifically because of Tiingo's 50/hour ceiling).

**7. `TIINGO_API_KEY` becomes optional at startup; Tiingo/Binance code and migrations are left in place.**
`Main.java`'s `requireEnv("TIINGO_API_KEY")` is replaced with the same `envOrEmpty`-style optional pattern already used for the Binance base-URL overrides — if absent, no Tiingo client is constructed and `providersByVenue` simply has no `EXCHANGE` entry (safe: zero active assets are `EXCHANGE`-venue after this change, so that map key is never looked up). This is the concrete mechanism behind "disconnect Tiingo for now" — the alternative of deleting `TiingoMarketDataProvider` entirely was rejected because "for now" signals an explicitly reversible, temporary state, not a permanent removal.

## Risks / Trade-offs

- **[Risk] MEXC's tokenized-equity pairs may have materially different (likely thinner) liquidity/history depth than either Binance's original tokenized contracts or Tiingo's real EOD data**, since they're a third, independent synthetic wrapper (Ondo) rather than either of the previously-used sources. → Mitigation: none built in; the existing `InvalidSymbolException`-driven auto-deactivation and W1's multi-week SuperTrend warm-up already tolerate sparse/noisy series, same posture taken for Tiingo's OTC ADRs.
- **[Risk] `GOOGLONUSDT` (Alphabet Class A) substitutes for the user's requested `GOOG` (Class C) since MEXC only wraps Class A** — the two share classes track near-identically in practice (same underlying company, near-zero historical price/voting-rights divergence) but are not literally the same instrument. → Mitigation: none needed beyond documenting the substitution here and in `asset-list.md`; revisit only if the two classes ever meaningfully diverge in price.
- **[Risk] Ticker-to-MEXC-symbol matching (both the direct crypto remap and the stock `xStocks`/Ondo lookup) was done programmatically against a live `exchangeInfo` snapshot, not manually verified company-by-company the way Tiingo's original 47 tickers were.** A handful of MEXC `fullName` values are sparse (bare ticker repeated, e.g. `DOGE`/`TIA`/`FET`) rather than a real company name, which weakens the cross-check for those specific rows. → Mitigation: the programmatic match already caught one real false-positive risk class (see Context — `BOSONUSDT`) and found zero wrong-coin mismatches across the 93 matched crypto tickers; still worth a final human skim of `asset-list.md` against the source lists before the seed migration ships, same spirit as the Tiingo precedent even if not identically manual.
- **[Risk] `MEXC:<SYMBOL>` may not resolve on TradingView for tokenized-stock tickers specifically**, leaving `tradingviewUrl` links broken for those assets even though ordinary crypto pairs resolve fine. → Mitigation: explicit live spot-check task before this change is considered complete; if it fails, `TradingViewUrl` would need a `tradingview_ref`-style override column for MEXC STOCK/ETF assets, structurally identical to what `EXCHANGE`/Tiingo already has — deferred as a follow-up if the spot-check fails rather than built speculatively now.
- **[Trade-off] Reduced provider diversity**: a single provider (MEXC) now sources 100% of active data, versus two independent providers today. If MEXC has an outage or delists a symbol, ingestion for that asset class has no fallback source anymore (Binance/Tiingo are dormant, not gone — reactivating them is the fallback, not automatic).
- **[Trade-off] Some real-equity coverage is lost outright**: the three China A-shares and any Tiingo ADR without a MEXC tokenized counterpart simply drop out of the active universe with this migration, since MEXC doesn't have every ticker Tiingo has.

## Migration Plan

1. New migration: `ALTER TYPE provider ADD VALUE 'MEXC'` (own migration file — cannot share a transaction with any statement using the new value).
2. New migration: `ALTER TYPE asset_venue ADD VALUE 'MEXC'`, same transactional constraint.
3. Code deploy: `Provider.MEXC`, `AssetVenue.MEXC`, `MexcMarketDataProvider`, `Main` wiring MEXC into `providersByVenue`, `TIINGO_API_KEY` made optional.
4. New seed migration inserting the remapped MEXC asset universe (`provider = 'MEXC'`, `venue = 'MEXC'`, `asset_class` per the classification rule in Decision 3, `active = true`).
5. New migration deactivating every `BINANCE`/`TIINGO` asset row (`active = false`) — run only after step 4's replacements are confirmed ingesting successfully, so there's no gap where an asset class has zero active assets in production (same failure mode `fix-weekly-briefing-empty-asset-class-npe` just fixed the symptom of, no reason to walk back into it operationally).
6. Order matters the same way it did for Tiingo: enum migrations (1-2) and code (3) must both be live before the seed migration (4) runs; the deactivation migration (5) is the last step, after step 4 is verified.
- **Rollback:** reactivate the Binance/Tiingo rows (`UPDATE asset SET active = true WHERE provider IN ('BINANCE','TIINGO')`) and deactivate the MEXC rows — no schema rollback needed, consistent with this project's established active-flag-based rollback convention. Restoring the `TIINGO_API_KEY` requireEnv check is a one-line code revert if Tiingo needs to become mandatory again.

- **[Risk, confirmed] 8 of the 118 onboarded assets have fewer than the ~147 daily bars W1 SuperTrend needs to warm up**, checked live across the full final list (not just a spot-check): `SPCXONUSDT` (75 bars, listed 2026-06-13), `SKHYONUSDT` (45, since 2026-07-13), `DELLONUSDT` (70, since 2026-06-18), `WFCONUSDT` (134, since 2026-04-15), `SAPONUSDT` (21, since 2026-08-06), and ETFs `IWFONUSDT` (134), `EFAONUSDT` (141), `SOXXONUSDT` (125) — all recently (re)launched tokenized wrappers, not a data-quality problem. → Mitigation: none needed; this is the same "not enough signal state yet" transient every newly-onboarded asset already goes through (existing behavior, not new to this change) and self-resolves as daily ingestion accumulates more bars over the following weeks/months.

## Open Questions

- Whether `MEXC:<tokenized-symbol>` actually resolves on TradingView — deferred to the spot-check task in Decision 4/Risks.
- Whether MEXC's tokenized-stock series have enough historical daily bars for the existing SuperTrend/W1 warm-up window (Tiingo's real EOD data had years of history; Ondo-wrapped tokens may only go back to their tokenization date) — worth a quick spot-check on 2-3 symbols' earliest `klines` bar during implementation, not resolved here.
