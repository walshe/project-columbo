<objective>
Implement `CandleRollupService` — a generic, timeframe-agnostic service that groups
finalized source candles into calendar weeks, aggregates each complete week into one
target candle, and persists it via idempotent upsert.

Purpose: This is the core deliverable of Phase 1. It must NOT hardcode D1 or W1 — the
roadmap explicitly requires the rollup to be reusable for future H4→D1 and H4→W1
callers (CNDL-04). The week grouping (CNDL-01), incomplete-week guard (CNDL-02), and
incremental detection are all expressed against `sourceTimeframe` / `targetTimeframe`
parameters. This plan delivers the service plus its unit-test coverage; cross-run
idempotency and DB-enum integration are verified end-to-end in plan 01-03.

Output: `CandleRollupService.java` (rollup logic) and `CandleRollupServiceTest.java`
(pure-Java unit tests for OHLCV correctness, the incomplete-week guard, and
timeframe-genericity).
</objective>

    1. Fetch source candles: `candleRepository.findByAssetAndTimeframeOrderByCloseTimeAsc(asset, sourceTimeframe)`.
       Return early if empty.
    2. Determine the last stored target close time:
       `candleRepository.findLatestCloseTime(asset.getId(), targetTimeframe.name())`,

       `openTime.withOffsetSameInstant(ZoneOffset.UTC).with(TemporalAdjusters.previousOrSame(weekStartDay)).withHour(0).withMinute(0).withSecond(0).withNano(0)`,

       chronologically ordered. The `weekStartDay` parameter — NOT a `DayOfWeek.MONDAY`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| D1 candle rows (DB) → rollup aggregation | Stored candle data is read and aggregated; a corrupt/incomplete row set could yield a wrong W1 candle |
| Rollup service → candle table writes | The service inserts/updates rows in a shared table — must not corrupt existing D1 data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Tampering | Week aggregation logic | mitigate | OHLCV computed only from candles within the grouped week; `open`/`close` taken from sorted-ascending data via `findByAssetAndTimeframeOrderByCloseTimeAsc` — no cross-week contamination |
| T-01-06 | Tampering | Target candle writes | mitigate | Idempotent upsert keyed on `(asset, targetTimeframe, closeTime)`; writes only target-timeframe rows — never modifies source (D1) rows |
| T-01-07 | Denial of Service | Per-asset rollup failure | mitigate | Each asset wrapped in try/catch (mirrors SuperTrendService) — one bad asset cannot abort the whole run |
| T-01-08 | Information Disclosure | Rollup logs | accept | Logs contain only asset symbols and row counts — no secrets or PII |
| T-01-09 | Elevation of Privilege | Service invocation | accept | Internal `@Service` bean — no HTTP exposure in this phase; access control N/A (RESEARCH.md Security Domain) |
| T-01-SC | Tampering | npm/pip/cargo installs | accept | No new packages — only JDK `java.time` and existing Spring/JPA dependencies (RESEARCH.md "installs zero external dependencies") |

V5 Input Validation is minimal — week boundary inputs derive from DB timestamps, not
user input (RESEARCH.md Security Domain). No new HTTP/auth surface.
</threat_model>
