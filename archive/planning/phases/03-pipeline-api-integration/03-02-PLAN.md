<objective>
Prove that all three existing query/scan endpoints — `GET /api/v1/market-pulse`,
`GET /api/v1/signals`, and `POST /api/v1/scan` — correctly serve W1 data when `timeframe=W1`
is requested. The endpoints already accept the `Timeframe` enum (W1 was added to the enum in
Phase 1), so no controller or query-service code change is required: the `timeframe` request
parameter / DTO field flows straight into the repository queries. This plan delivers the
integration tests that verify W1 actually round-trips through each endpoint and that W1 responses
contain only W1 data.

Purpose: API-01 (market-pulse supports W1), API-02 (signals query supports W1), API-03 (scan
supports W1 in conditions).
Output: New `W1ApiIntegrationTest` covering all three endpoints with W1 fixtures.
</objective>

Endpoints under test (all already accept the Timeframe enum — no production code change needed):
  GET  /api/v1/market-pulse?timeframe={TF}&indicatorType={IT}
       -> MarketPulseController.getLatestPulse -> MarketPulseQueryService
          .repository.findTopByTimeframeAndIndicatorTypeOrderBySnapshotCloseTimeDesc(timeframe, indicatorType)
       -> 200 + MarketPulseDto, or 404 if no snapshot.
  GET  /api/v1/signals?timeframe={TF}&indicatorType={IT}[&state=&sort=]
       -> SignalController.getSignals -> SignalQueryService.listSignals(...)
          Query is timeframe-scoped via signalStateRepository.findLatestFinalizedForActiveAssets(timeframe, ...).
  POST /api/v1/scan  body: ScanRequest
       -> ScanController.scan -> ScanService.execute -> queries scoped by request.timeframe().

ScanRequest record (backend/.../api/v1/scan/dto/ScanRequest.java):
  record ScanRequest(Timeframe timeframe, ScanOperator operator, List<ScanCondition> conditions, Integer limit)
ScanCondition record (backend/.../api/v1/scan/dto/ScanCondition.java):
  ScanCondition(IndicatorType indicatorType, SignalEvent event, TrendState state,
                Integer maxDaysSinceFlip, Integer maxDaysSinceCross)
ScanValidator: validates indicator/event/state combos — DOES NOT constrain timeframe (W1 passes validation).

Entities for fixture seeding:
  MarketBreadthSnapshot constructor (used in ApiIntegrationTest):
    new MarketBreadthSnapshot(Timeframe, IndicatorType, OffsetDateTime snapshotCloseTime,
                              int bullishCount, int bearishCount, int unknownCount, int totalCount,
                              BigDecimal bullishRatio)
  SignalState: new SignalState(Asset, Timeframe, IndicatorType, OffsetDateTime closeTime,
                               TrendState, SignalEvent)  — OR no-arg + setters (both used in codebase)
  Asset: new Asset(String symbol, String name, MarketProvider, boolean active)
  Candle: no-arg constructor + setters (setAsset/setTimeframe/setOpenTime/setCloseTime/
          setOpen/setHigh/setLow/setClose/setVolume/setSource)
  RsiIndicator: no-arg + setAsset/setTimeframe/setCloseTime/setRsiValue

Enum values: IndicatorType.SUPERTREND, IndicatorType.RSI; TrendState.BULLISH, BEARISH;
  SignalEvent.BULLISH_REVERSAL, BEARISH_REVERSAL, CROSSED_ABOVE_60, NONE.

ScanService.getLatestFinalizedCloseTime(timeframe) reads
  candleRepository.findLatestCloseTimeForTimeframe(timeframe.name()) — so the scan test MUST seed
  at least one W1 Candle (not just a SignalState) for the asset, or the scan close-time window
  defaults to now-truncated and finalized W1 signals may be excluded. Seed W1 candles with closeTime
  at "now truncated to day" (matching the SignalState closeTime) so signals fall inside the window.
</interfaces>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Tampering | `timeframe` request param / `ScanRequest.timeframe` field accepting arbitrary input | mitigate | Spring binds the param to the `Timeframe` enum; an unknown value yields HTTP 400 via `GlobalExceptionHandler` ("Invalid Parameter Value"). `W1` is a legitimate enum constant. No SQL injection surface — repository queries are parameterized JPA. Existing `ApiIntegrationTest.shouldReturn400ForInvalidParams` already covers the rejection path. |
| T-03-05 | Information Disclosure | W1 endpoints leaking D1 rows or vice versa | mitigate | Every endpoint query is timeframe-scoped at the repository layer; the new tests explicitly seed both D1 and W1 fixtures and assert only W1 data is returned (no cross-timeframe leakage). |
| T-03-06 | Denial of Service | Scan over W1 with many conditions | accept | Scan is bounded by active-asset count and the existing `limit` cap (default 100). W1 adds no new unbounded path — same query shape as D1. |

No production code modified, no new HTTP endpoints, no package installs — `T-{phase}-SC` not applicable. This plan adds test coverage only; the endpoints already accept the `Timeframe` enum.
</threat_model>
