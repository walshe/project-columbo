<objective>
Update the output DTOs (`MatchedIndicator`, `SupertrendMatch`, `RsiMatch`) to include a `timeframe` field,
then update `ScanValidator` and `ScanService` to enforce and execute per-condition timeframe resolution.

After this plan, a scan request with mixed-timeframe conditions is evaluated correctly: each condition
queries its own timeframe's data, the AND intersection operates across all timeframes, and each
`MatchedIndicator` in the response carries the timeframe it came from.

Purpose:
- SCAN-03: Validator rejects requests where any condition has no resolvable timeframe
- SCAN-05: AND logic applies across all conditions regardless of timeframe
- SCAN-06: Each condition uses the latest finalized close time for its own timeframe
- SCAN-07: Asset intersection (AND pruning) operates on timeframe-agnostic asset IDs
- SCAN-08: MatchedIndicator subtypes include timeframe field
- SCAN-09: ScanResponse echoes conditions including per-condition timeframes
- SCAN-10: TradingView URL uses highest-granularity timeframe among matched indicators

Output: Five modified Java files (DTOs + validator + service); main sources compile cleanly.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → ScanController → ScanService | Scan request with mixed timeframes crosses here; each timeframe is a validated enum value |
| ScanService → DB (multi-timeframe queries) | Per-condition queries to signalStateRepository with different Timeframe values |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-03 | Tampering | Per-condition timeframe bypassing validation | mitigate | ScanValidator.resolveTimeframe() enforces that every condition has a resolvable timeframe before execution. Invalid timeframe enum values are rejected by Spring binding (400 before the service is called). |
| T-04-04 | Denial of Service | N conditions across M unique timeframes requiring M×N repository queries | accept | The number of unique timeframes is bounded by the Timeframe enum size (currently 2: D1, W1). The close-time map is built once per unique timeframe, not per condition. Repository queries remain the same shape as before — no new unbounded paths introduced. |
| T-04-05 | Information Disclosure | Cross-timeframe data leakage (W1 signals appearing in D1 results) | mitigate | Each condition resolves an explicit effectiveTf and passes it to signalStateRepository queries. The repository is already timeframe-scoped at the SQL level. The AND intersection operates on asset IDs only — no timeframe cross-contamination possible. Integration test in plan 04-03 verifies this explicitly. |
| T-04-06 | Repudiation | TradingView URL timeframe mismatch (URL shows wrong timeframe) | mitigate | highestTimeframe() picks W1 over D1, consistent with the Bullmania strategy intent. If no indicators are present (empty scan), falls back to D1. Unit test in 04-03 verifies the priority logic. |

No new HTTP endpoints, no package installs, no external calls beyond existing repository layer.
